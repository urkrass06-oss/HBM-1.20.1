# Feature-Lücken: Original, Modernized und geprüfte Integration

Stand: **20.10.2026**, Ziel-`main` **`ff1eef39e870b9e4322d7a2d8b30f6bb3a517044`**. Diese Matrix ergänzt die unveränderte [Originalmatrix mit 140 Funktionsfamilien](FEATURE_MATRIX.md), deren historische Portstatus nicht als aktueller Integrationsnachweis gelesen werden dürfen. Sie ersetzt keine Einzelinventur sämtlicher Registry-IDs, Varianten, Rezepte oder Assets und streicht keinen Originalumfang.

Die beiden fixierten Quellbäume wurden separat ausgecheckt. Für Prioritätslücken wurden ausführbare Methoden, Block-/Item-/BE-Register und Ressourcenpfade erneut gelesen; für den übrigen Umfang wird der vorhandene [Vergleich](MODERNIZED_COMPARISON.md#4-originalfunktionen-und-tatsächlicher-modernized-bestand) mit ausdrücklicher Prüfgrenze fortgeführt. Anker der vollständigen Tabelle sind **Einstiegspunkte**, keine Behauptung, dass eine einzelne Klasse die ganze Zeile implementiert. Ein O-Java-Symbol wird nicht als tatsächlicher alter Registryname ausgegeben: `ModBlocks.register()`/`ModItems` übergeben oft `getUnlocalizedName()`, Metadaten und historische Aliase bleiben getrennt zu inventarisieren.

| Kennung | Aussage |
| --- | --- |
| A | Ausführbarer Teilbestand und Anbindung belegt; keine automatische O-Parität |
| T | Konkrete Teilimplementierung oder Platzhalter vorhanden |
| L | Bestimmte Implementierungslücke direkt belegt; ihr genauer Umfang steht in der Zeile |
| U | Fachpfad/Abdeckung unzureichend geprüft; **keine gesicherte Fehlfunktion oder Abwesenheit** |

Mehrere Kennungen trennen Teilaspekte. Die Prüfspalte nennt nur tatsächlich belegte Teiltests oder die fehlende Abnahme. Keine Familie ist hier pauschal „originalverifiziert“. Ein fehlender Dateiname, weniger Assets oder ein TODO allein beweist keine fehlende Funktion. „Kein Gegenstück nachgewiesen“ bedeutet eine begrenzte Inventurlücke, keine bewiesene globale Abwesenheit.

## Reproduktion und Abschlussregeln

```bash
# Separate unveränderte Checkouts O und M anlegen und ihre oben genannten SHAs prüfen.
git -C "$O" rev-parse HEAD
git -C "$M" rev-parse HEAD
git -C "$M" ls-tree -r --name-only HEAD src/main/java src/main/resources
rg -n 'canProcess|processItem' "$M/src/main/java/com/hbm_m/blockentity/machines/MachineBreederBlockEntity.java"
rg -n 'PWR_CONTROLLER|FUSION_COMPONENT|ICF_CONTROLLER|ELECTROLYSER|ROTARY_FURNACE|CONVEYOR' "$M/src/main/java/com/hbm_m/block/ModBlocks.java"
# Aus dem Zielrepository:
HBM_ORIGINAL_SOURCE="$O" python3 -m unittest discover -s tools -p 'test_inventory_original.py' -v
python3 tools/inventory_original.py --source "$O" --check
```

Vor jeder Featurelieferung die vollständige Registrierungskette und Erreichbarkeit, Varianten/Rezepte/Ressourcen sowie den tatsächlichen O-/M-Ausführungspfad erfassen. Bei einem bisher als U geführten Bereich zunächst einen gezielten Fachtest ausführen: funktioniert er bereits, Implementierung erhalten und als Teilnachweis dokumentieren; schlägt er nachweislich fehl, anschließend den konkreten Prozess portieren/korrigieren. Keine neue allgemeine Planungsphase als Taskabschluss.

Einzelabnahmen werden nur mit Code, Tests und belegtem Umfang fortgeschrieben: Implementiert → getestet auf I → originalverifiziert nach tatsächlichem O-Vergleich. Für unbekannte Varianten bleibt die Familie offen. [Gemeinsame Gates und Dateibesitz](PARALLEL_DEVELOPMENT.md) sowie [Importcheckliste](MODERNIZED_IMPORT_CHECKLIST.md) gelten zusätzlich. Rechteoffene Ressourcen bleiben extern; dieser Auftrag veröffentlicht keine fremden Assetbytes oder neuen Vollquellen.
